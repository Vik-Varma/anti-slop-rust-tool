# What primary Rust sources call bad Rust code

Research for a syntax-only (syn AST) Rust linter. Every quote below was checked against a page fetched on 2026-10-26, or against the Clippy source at commit `43c0efca149bb15b9cd2bbf2ef34771cefa70a7e` (rust-lang/rust-clippy `master`, 2026-10-24). Quotes are verbatim; where a line break or inline-code marker was dropped by text extraction, only whitespace and backticks differ.

## How to read this

- **Authority** is the kind of source. **Normative** means the source is binding in its context: the Reference, compiler behaviour, or the MUST rules of a guideline. **Official guidance** means rust-lang documentation that recommends something. **Tool policy** means a Clippy lint's own justification. **Community** means a well-known guide that is not rust-lang official.
- **Hedge** is the source's own qualification. Report it with any finding.
- **Clippy groups** come from the Clippy README (https://github.com/rust-lang/rust-clippy/blob/master/README.md):
  - `correctness` is "code that is outright wrong or useless" (deny).
  - `suspicious` is "code that is most likely wrong or useless" (warn).
  - `complexity` is "code that does something simple but in a complex way" (warn).
  - `pedantic` is "lints which are rather strict or have occasional false positives" (allow).
  - `restriction` is "lints which prevent the use of language and library features" (allow).
  - The README also says: "The `restriction` category should, *emphatically*, not be enabled as a whole. The contained lints may lint against perfectly reasonable code, may not have an alternative suggestion, and may contradict any other lints (including other categories)."
  - **A restriction-group lint is therefore a project policy, not evidence that the code is bad.**
- **Clippy URLs**:
  - Published docs are at `https://rust-lang.github.io/rust-clippy/master/index.html#<lint>`.
  - Source is at `https://github.com/rust-lang/rust-clippy/blob/43c0efca149bb15b9cd2bbf2ef34771cefa70a7e/clippy_lints/src/<file>`.
  - I cross-checked eight groups against the published index: cognitive_complexity, excessive_nesting, float_cmp, fn_params_excessive_bools, await_holding_lock, let_underscore_future, cast_possible_truncation and too_many_lines. All eight matched.
- **Defaults for thresholds** come from `clippy_config/src/conf.rs` at the same commit.
- **Syntax-only limits**: syn has no types and no name resolution. Any check that needs "receiver is `Result`" or "type implements `Drop`/`Future`/`#[must_use]`" is a heuristic.

| CLP-24 | `panic_in_result_fn` (restriction), panic_in_result_fn.rs | `panic!`/`assert!` etc. inside fn returning `Result` | "For some codebases, it is desirable for functions of type result to return an error instead of crashing. | CLP-25 | `indexing_slicing` (restriction), indexing_slicing.rs | `a[i]`, `a[x..y]` | "To avoid implicit panics from indexing and slicing." | Restriction. `allow-indexing-slicing-in-tests`. | CLP-26 | `arithmetic_side_effects` (restriction), operators/mod.rs | Any `+ - * << / %` etc. | "For integers, overflow will trigger a panic in debug builds or wrap the result in release mode; division by zero will cause a panic in either mode. It ignores floats, `Wrapping`/`Saturating`, const contexts and ops that provably can't overflow. | `ExprBinary` arithmetic ops. **FPs:** extreme, because syn can't tell floats or wide types apart. Use it only as an opt-in policy (matches ANSSI LANG-ARITH). |

## 2. std docs, the Book, the Reference and the Edition Guide

| ID | Pattern | Claimed harm (verbatim) | URL | Authority | Hedge | syn detection / FPs |
|---|---|---|---|---|---|---|
| STD-01 | Panicking in `Drop::drop` | "Implementations should generally avoid panic!ing, because drop() may itself be called during unwinding due to a panic, and if the drop() panics in that situation (a “double panic”), this will likely abort the program." | https://doc.rust-lang.org/std/ops/trait.Drop.html (§Panics) | Official guidance | "generally". It allows checking `panicking()` first for "you didn't finish using this" bug reports. | In `impl Drop for X { fn drop }`, find `panic!`/`unwrap`/`expect`/`assert!`/`unreachable!`/`todo!`, plus indexing if strict. **FPs:** guarded by `if !std::thread::panicking()`, which you should exempt. **Precise.** |
| STD-02 | `mem::forget` | "That said, leaking resources such as memory or I/O objects is usually undesirable. The need comes up in some specialized use cases for FFI or unsafe code, but even then, ManuallyDrop is typically preferred." | https://doc.rust-lang.org/std/mem/fn.forget.html | Official guidance | "usually". "forget is not marked as unsafe, because Rust’s safety guarantees do not include a guarantee that destructors will always run." | Call path `mem::forget`. **FPs:** FFI ownership transfer. |
| STD-03 | `mem::uninitialized` (deprecated since 1.39.0) | "This function is deprecated. Use MaybeUninit<T> instead." / "Therefore, it is immediate undefined behavior to call this function on nearly all types, including integer types and arrays of integer types, and even if the result is unused." | https://doc.rust-lang.org/std/mem/fn.uninitialized.html | Normative (deprecated; UB) | "nearly all types" | Path `mem::uninitialized`. **Precise.** rustc also warns (deprecated). |
| STD-04 | Zeroed or uninit values asserted initialised | "As a consequence, zero-initializing a variable of reference type causes instantaneous undefined behavior, no matter whether that reference ever gets used to access memory" (the docs' example: `let b: bool = unsafe { MaybeUninit::uninit().assume_init() }; // undefined behavior! ⚠️`) | https://doc.rust-lang.org/std/mem/union.MaybeUninit.html | Normative (UB) | Initialization invariant depends on the type; padding need not be initialised. | `MaybeUninit::uninit().assume_init()` (CLP-19). `mem::zeroed()` with a `let x: &T` / `bool` / `NonNull` / `Box` / fn-pointer annotation. Precise when annotated. |
| STD-05 | `process::exit` skips destructors | "Note that because this function never returns, and that it terminates the process, no destructors on the current stack or any other thread’s stack will be run." | https://doc.rust-lang.org/std/process/fn.exit.html | Official guidance | It recommends calling it only where no destructors remain, "or, preferably, simply return a type implementing Termination (such as ExitCode or Result) from the main function and avoid this function altogether". | Path `process::exit`. **FPs:** at the end of `main`, which is acceptable per the docs. |
| STD-06 | References to `static mut` (2024 edition) | "In the 2024 Edition, this lint is now deny by default to emphasize that you should avoid making these references." / "Merely taking such a reference in violation of Rust’s mutability XOR aliasing requirement has always been instantaneous undefined behavior, even if the reference is never read from or written to." | https://doc.rust-lang.org/edition-guide/rust-2024/static-mut-references.html | Normative (`static_mut_refs` lint is deny in 2024) | "In some cases it may be safe to create a reference of a static mut. The whole point of the static_mut_refs lint is that this is very hard to do correctly!" Recommended alternative: "an immutable static of a type that provides interior mutability". | Flag `ItemStatic` with `mutability: Mut` (a declaration-level smell), and `&`/`&mut` of a path naming a same-file `static mut`. **Precise** for same-file names. FPs: `&raw const/mut` is the sanctioned form. |
| STD-07 | Integer overflow in release builds | "When you’re compiling in release mode with the --release flag, Rust does not include checks for integer overflow that cause panics. Instead, if overflow occurs, Rust performs two’s complement wrapping." / "Relying on integer overflow’s wrapping behavior is considered an error." | https://doc.rust-lang.org/book/ch03-02-data-types.html ; Reference: "Integer operators will panic when they overflow when compiled in debug mode." https://doc.rust-lang.org/reference/expressions/operator-expr.html#overflow | Book: official guidance. Reference: normative. | The Book offers `wrapping_*`, `checked_*`, `overflowing_*` and `saturating_*` alternatives. | Syntax alone can't tell overflow-prone arithmetic apart (see CLP-26). It is precise only for literal-only overflowing expressions, which rustc already catches. |
| STD-08 | Dropping a `BufWriter` without `flush` | "It is critical to call flush before BufWriter<W> is dropped. Though dropping will attempt to flush the contents of the buffer, any errors that happen in the process of dropping will be ignored." | https://doc.rust-lang.org/std/io/struct.BufWriter.html | Official guidance | None. | In a fn body, `let w = BufWriter::new(..)` with no `w.flush()`/`w.into_inner()` before scope end and `w` not returned or moved. **FPs:** writer passed to a fn that flushes; returned writers. Medium precision. |
| STD-09 | Mutex poisoning | "Once a mutex is poisoned, all other threads are unable to access the data by default as it is likely tainted (some invariant is not being upheld)." / "Most usage of a mutex will simply unwrap() these results, propagating panics among threads to ensure that a possibly invalid invariant is not witnessed." | https://doc.rust-lang.org/std/sync/struct.Mutex.html (§Poisoning) | Official guidance | "Poisoning is only advisory: the PoisonError type has an into_inner method". **The std docs endorse `.lock().unwrap()`.** | Do *not* flag `.lock().unwrap()` as bad. If anything, flag `PoisonError::into_inner`/`unwrap_or_else(|e| e.into_inner())` for review, because it ignores a possibly broken invariant. |

## 3. Tokio

| ID | Pattern | Claimed harm (verbatim) | URL | Authority | Hedge | syn detection / FPs |
|---|---|---|---|---|---|---|
| TOK-01 | Blocking or long compute inside async | "In general, issuing a blocking call or performing a lot of compute in a future without yielding is problematic, as it may prevent the executor from driving other futures forward." | https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html | Official guidance (Tokio) | "In general". Also: "Tasks should generally not perform system calls or other operations that could block a thread, as this would prevent other tasks running on the same thread from executing as well." (https://docs.rs/tokio/latest/tokio/task/index.html) | Inside `async fn`/`async {}` (not inside `spawn_blocking` closures), find calls to `std::thread::sleep`, `std::fs::*`, `std::net::TcpStream::connect`, `reqwest::blocking`, `.blocking_lock()`, or `std::io::stdin().read_line`. **FPs:** fast fs calls during startup; code under `block_in_place`. |
| TOK-02 | std `Mutex` guard across `.await` | "Note that, although the compiler will not prevent the std Mutex from holding its guard across .await points in situations where the task is not movable between threads, this virtually never leads to correct concurrent code in practice as it can easily lead to deadlocks." | https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html | Official guidance | "Contrary to popular belief, it is ok and often preferred to use the ordinary Mutex from the standard library in asynchronous code." ## 4. Rust Design Patterns (community) and Rust API Guidelines (official, rust-lang)

| ID | Pattern | Claimed harm (verbatim) | URL | Authority | Hedge | syn detection / FPs |
|---|---|---|---|---|---|---|
| DP-01 | Clone to satisfy the borrow checker | "Using .clone() causes a copy of the data to be made. Any changes between the two are not synchronized – as if two completely separate variables exist." | https://rust-unofficial.github.io/patterns/anti_patterns/borrow_clone.html | Community (rust-unofficial) | "Rc<T> is designed to handle clones intelligently." and "If a clone is used to make a borrow checker error disappear, that’s a good indication this anti-pattern may be in use." The page itself defers to `cargo clippy` for unnecessary clones. | syn can't see intent. Narrow heuristics: `&mut x.clone()` / `&mut (x.clone())` (mutating a temporary copy, as in the page's own example); `.clone()` immediately borrowed `&x.clone()`. **FPs:** Rc/Arc clones. |
| DP-02 | `#![deny(warnings)]` in crate source | "By disallowing the compiler to build with warnings, a crate author opts out of Rust’s famed stability." | https://rust-unofficial.github.io/patterns/anti_patterns/deny-warnings.html | Community | Alternatives: set `RUSTFLAGS="-D warnings"` in CI, or deny named lints. | Inner attribute `#![deny(warnings)]` (or `forbid(warnings)`). **Precise.** |
| DP-03 | Deref polymorphism (Deref to emulate inheritance) | "Most importantly this is a surprising idiom - future programmers reading this in code will not expect this to happen. That’s because we are misusing the Deref trait rather than using it as intended (and documented, etc.)." | https://rust-unofficial.github.io/patterns/anti_patterns/deref.html | Community | None beyond the page's own discussion. | `impl Deref for S { type Target = T }` where `S` is a same-file struct with a field of type `T`, and `T` is not a pointer or wrapper-like type. **FPs:** legitimate newtype/smart-pointer wrappers (`Deref<Target=[T]>`, `str`). Medium. |
| API-01 | C-DTOR-FAIL: fallible destructors | "Destructors are executed while panicking, and in that context a failing destructor causes the program to abort." | https://rust-lang.github.io/api-guidelines/dependability.html#c-dtor-fail | Official guidance (rust-lang API Guidelines) | It proposes "a separate method for checking for clean teardown, e.g. a close method, that returns a Result". | Same as STD-01. |
| API-02 | C-GOOD-ERR: `()` or non-`Error` error types | "Never use () as an error type, even where there is no useful additional information for the error to carry." | https://rust-lang.github.io/api-guidelines/interoperability.html#c-good-err | Official guidance | Scoped to "any type E used in a Result<T, E> returned by any public function of your crate". | `pub fn` returning `Result<_, ()>`: **precise**. A same-file `pub` error type with no `impl Error for` it is a heuristic, because the impl may be elsewhere. |
| API-03 | C-CUSTOM-TYPE: `bool`/`Option` args instead of meaningful types | "Core types like bool, u8 and Option have many possible interpretations." | https://rust-lang.github.io/api-guidelines/type-safety.html#c-custom-type | Official guidance | It frames this as "Prefer `Widget::new(Small, Round)` over `Widget::new(true, false)`". It sets no threshold. | Call-site `true`/`false` literals as arguments (≥2), or `pub fn` with `bool` params. **FPs:** setters like `set_visible(bool)`. |

## 5. ANSSI Secure Rust Guidelines

Source: https://anssi-fr.github.io/rust-guide/print.html (all chapters; anchors are `#<ID>`). Authority: a national security agency guide (France), aimed at "secure development". MUST and SHOULD keep their RFC-style strength. The rules below are every rule or recommendation that forbids or discourages a pattern. Wording is the guide's text, verbatim.

| ID | Type | Wording (verbatim) | syn detection / FPs |
|---|---|---|---|
| DENV-STABLE | Rule | "Development of a secure application MUST be done using a fully stable toolchain, for limiting potential compiler, runtime or tool bugs." | `#![feature(..)]` inner attribute: **precise**. |
| DENV-CARGO-OPTS | Rule | "The variables debug-assertions and overflow-checks MUST NOT be overridden in development profiles’ sections ([profile.dev] and [profile.test])." | Not syn; it needs a Cargo.toml check. |

## Disagreements with the repository

I compared these findings with `/home/user/anti-slop-rust-tool/docs/EVIDENCE.md` and `/home/user/anti-slop-rust-tool/src/rules.rs`, and re-fetched every page the repo cites that falls in this report's scope (2026-10-26). The repo's Clippy groups are all correct: `unwrap_used`, `dbg_macro` and `undocumented_unsafe_blocks` are restriction; `await_holding_lock` is suspicious; `unused_io_amount` is correctness and deny by default. Its `cognitive_complexity` quotes are verbatim. The other quotes I checked also match their pages:

- the Book ch. 9.2 `expect` line;
- the Tokio "would otherwise block other tasks from running" line;
- the `BufWriter` drop line;
- "`dbg!` works exactly the same in release builds";
- the `static_mut_refs` deny-by-default wording.

### Misquotes and overstatements

1. **`unwrap` rule: the Book is misquoted.** `rules.rs` (rule `unwrap`, harm) says "The Rust Book accepts unwrap where the code knows more than the compiler".
   - The current Book ch. 9.3, section "When You Have More Information Than the Compiler", is about **`expect`**, not `unwrap`: "If you can ensure by manually inspecting the code that you’ll never have an Err variant, it’s perfectly acceptable to call expect and document the reason you think you’ll never have an Err variant in the argument text." (https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html)
   - Older editions of the Book used `unwrap` here.
   - Fix: say the Book accepts `expect` with a stated reason in that case, and accepts `unwrap` only for prototypes, examples and tests (same chapter: "the unwrap and expect methods are very handy when you’re prototyping").
2. **`todo` rule: the `unimplemented!` docs are overstated.** `rules.rs` says "the std docs define it as a statement that the code won't be implemented".
   - std says only that `unimplemented!` "makes no such claims" (about implementing the code later), and that it suits "implementing a trait that requires multiple methods which you don’t plan to use all of" (https://doc.rust-lang.org/std/macro.unimplemented.html).
   - EVIDENCE.md words this correctly ("it makes no claim the code will be written"). rules.rs should match it.
   - Separately, Clippy gives `unimplemented` exactly the same rationale as `panic` (CLP-05). Exempting it is the repo's own audit-based choice, not a source distinction.
3. **`unsafe-without-comment` overstates the scope of the policy.** It is called "the Rust project's own policy".
   - The std-dev guide scopes it to rust-lang's own code and uses "should": "Using unsafe blocks is often required in the Rust compiler or standard library, but this is not done without rules: each unsafe block should have a SAFETY: comment" (https://std-dev-guide.rust-lang.org/policy/safety-comments.html).
   - For user code, the only sources are Clippy's restriction-group lint (which Clippy says should not be enabled wholesale) and ANSSI LANG-UNSAFE / LANG-UNSAFE-ENCP.
   - Labelling it Consensus is fine. "Rust project policy for rustc/std" would be more precise.
4. **`static-mut`: the stated harm differs from the source's harm.** The repo rests the harm on data races. The Edition Guide's harm is narrower and stronger: taking any reference "has always been instantaneous undefined behavior, even if the reference is never read from or written to" (STD-06).
   - The guide's deny lint targets *references*, not the `static mut` item.
   - It explicitly allows `&raw const/mut` and narrow `allow`s. That is consistent with the repo's Note severity, but the cited source supports a reference check more than a declaration check (see omission O-1).
5. **`blocking-sleep-in-async`: "False positives: None in async code" is stronger than the source.**
   - Tokio's own wording is hedged: "In general, issuing a blocking call ... is problematic" and "Tasks should generally not perform system calls".
   - Code run under `tokio::task::block_in_place` (a sync closure, so probably already exempt) and non-Tokio executors aren't addressed.
   - This is minor.
6. **No mis-grouping found.** EVIDENCE.md's "Clippy reached the same place" paragraph on `cognitive_complexity` is accurate.

### Well-sourced patterns the repo omits that a syntax-only check can detect precisely

|---|---|---|---|
| O-1 | `&STATIC` / `&mut STATIC` where `STATIC` is a same-file `static mut` (2021-edition crates still only warn) | Edition Guide (STD-06): "this lint is now deny by default to emphasize that you should avoid making these references" | Name lookup within one file; `&raw` is syntactically distinct. |
| O-2 | `pub fn ... -> Result<_, ()>` | API Guidelines C-GOOD-ERR: "Never use () as an error type, even where there is no useful additional information for the error to carry." | Pure signature match. |

This is a warn-by-default lint, stronger than the restriction lint the repo already uses. |
| O-4 | `let _ = async { .. };` or `let _ = <same-file async fn>(..);` | Clippy `let_underscore_future` (suspicious): "Futures must be polled for work to be done." | Precise for literal async blocks and local async fns. |

The repo also deliberately dropped `mem-forget`, against ANSSI MEM-FORGET ("MUST NOT be used") and MEM-LEAK (`Box::leak`). That is defensible: ANSSI targets secure development, std says forget is only "usually undesirable", and Clippy's lint is restriction. But EVIDENCE.md doesn't mention that ANSSI forbids it outright. A reader of the drop table should see that.
